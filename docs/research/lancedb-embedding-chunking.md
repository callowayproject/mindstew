# LanceDB Embedding & Chunking Strategy — Research

Research for [issue #5](https://github.com/callowayproject/mindstew/issues/5), part of the Wayfinder map [#1](https://github.com/callowayproject/mindstew/issues/1). No decision made — this surfaces facts for a later grilling/decision ticket and to unblock [#10](https://github.com/callowayproject/mindstew/issues/10) (vector search integration into ingest).

## 1. LanceDB table schema & row-key design

- A LanceDB table is columnar (Lance format): one fixed-width vector column plus arbitrary metadata columns, created from a list of dicts/Arrow table/Pydantic model (`db.create_table("chunks", data)`). Source: [Basic Table Operations](https://docs.lancedb.com/tables).
- For a wiki with derived, rebuildable vector index (per issue #1's Decisions-so-far), the natural mapping is **one table, one row per chunk** (not one row per page): `page_path` (the `.md` file's relative path — the join key back to the source of truth), `chunk_id` (page_path + ordinal or heading slug), `content_sha256` (see §4), `heading_trail`, `text`, `vector`, plus copies of the frontmatter fields used for filtering (`tags`, `sources`, `created`, `aliases`). A second, optional page-level table (or a `chunk_id IS NULL`/aggregate view) is unnecessary — hybrid search and filters both work at chunk granularity, and the page path ties results back to the vault.
- Recommended primary/join key: `chunk_id` (stable, deterministic — e.g. `sha256(page_path + heading_path)[:16]` or `f"{page_path}#{ordinal}"`), not an autoincrement id, so re-embedding is a pure key-based upsert (§4).

## 2. Upsert / delete patterns (primary source: LanceDB docs)

- **Upsert = `merge_insert`**: `table.merge_insert("chunk_id").when_matched_update_all().when_not_matched_insert_all()` — updates rows whose key matches, inserts rows whose key doesn't. This is the exact primitive for "re-embed a page whose content changed." Source: [Updating and Modifying Table Data](https://docs.lancedb.com/tables/update).
- `merge_insert` performs a join on the key column; LanceDB explicitly recommends a **scalar index on the join column** (`chunk_id`) once the table has any meaningful size, to avoid a full scan per ingest run.
- Partial-column merges are supported — matched rows only overwrite the columns present in the incoming batch, so a re-embed can send just `{chunk_id, text, vector, content_sha256}` without re-supplying every metadata column, if desired (though for wiki edits, frontmatter usually changes too, so sending the full row is simpler and safer).
- **Deleting stale chunks**: when a page is deleted, or when re-chunking changes chunk boundaries/count for a page, use `table.when_not_matched_by_source_delete()` as a clause on the same `merge_insert` call (scoped by a `page_path = '...'` prefilter on the source batch) — or a plain `table.delete(f"page_path = '{page_path}'")` before re-inserting that page's chunks. `delete()` is a soft/versioned delete (marks rows deleted; `table.optimize()` reclaims space later) — safe to call per-page on every re-ingest of a changed page. Source: [Updating and Modifying Table Data](https://docs.lancedb.com/tables/update).
- **Hybrid search**: `table.search(query, query_type="hybrid")` combines a vector search (`.vector()`) and BM25 full-text search (`.text()`, via LanceDB's embedded Tantivy FTS index, `table.create_fts_index("text")`), fused by default with reciprocal-rank fusion (`RRFReranker`). Metadata `where=` filters (e.g. `tags LIKE '%project-x%'`) apply to both legs pre- or post-filter. This is the retrieval shape for the wiki: keyword-exact hits on titles/tags plus semantic recall in one call. Source: [LanceDB — Hybrid Search](https://lancedb.com/documentation/guides/search/hybrid-search.html).
- At wiki scale (thousands, not millions, of chunks) a vector index (`create_index()`, IVF_PQ/HNSW) is optional — brute-force flat scan is fast enough; add the index only once latency actually shows up.

## 3. Chunking strategy for Markdown wiki pages with frontmatter

- Upstream `llm_wiki` (the app being reimplemented, per issue #1) does not chunk: one wiki page = one embedded row, generated by its two-step CoT ingest, with vector search explicitly a *supplement* to keyword search, not primary. Source: [nashsu/llm_wiki README](https://github.com/nashsu/llm_wiki).
- Common practice for Obsidian-style Markdown RAG (surveyed across current OSS wiki/notes RAG tooling): **heading-aware chunking** — split each page on H2/H3 boundaries so each chunk is one coherent section, carrying its heading trail (`H1 > H2 > H3`) as a metadata column. Fixed-size token windows (e.g. 512 tokens) are the commonly-cited failure mode for header-structured notes because they cut mid-section; they're a fallback only for a section that's unusually long (target ~1500–2000 chars per chunk with ~15% overlap when splitting an oversized section).
- Frontmatter is parsed and stripped before chunking — never embedded as prose — and its structured fields (`tags`, `sources[]`, `created`, `aliases`) are copied onto **every chunk row** for that page (not just a page-level row), so a single LanceDB `where=` predicate scopes hybrid search by tag/date without a join back to the vault file.
- Recommendation for this app: **chunk per H2 section** (fall back to whole-page for pages with no H2s, which given the two-step CoT ingest's regularity should be uncommon), each chunk = frontmatter fields (copied) + heading trail + section text + embedding. This keeps chunk boundaries aligned with the app's own generated structure rather than an arbitrary token window, and keeps the LanceDB row shape simple (no separate page-table join needed for filtering).

## 4. Interaction with the SHA256 content cache (incremental re-embedding)

- Per issue #1, ingest already maintains an incremental SHA256 content-hash cache to skip unchanged sources at the CoT step. The same hash should drive re-embedding, extended to chunk granularity:
  1. On ingest, after a page's Markdown is (re)written, compute `content_sha256` over the **chunk's own text** (post-chunking, not the whole page) — this way, editing one section of a page only invalidates that section's chunk, not the whole page's embeddings.
  2. Before calling the embeddings API, look up the page's existing chunk rows in LanceDB by `page_path` prefix and compare `content_sha256` per `chunk_id`. Unchanged hash → skip the embedding call entirely (cache hit, mirrors the existing ingest-level SHA256 cache); changed or new hash → embed and stage for `merge_insert`.
  3. Run one `merge_insert("chunk_id")` per changed page: `when_matched_update_all()` for changed chunks, `when_not_matched_insert_all()` for new chunks (section added), and `when_not_matched_by_source_delete()` scoped to that page's chunks for removed sections (section deleted or heading restructured, changing chunk_ids).
  4. This makes LanceDB a **derived, rebuildable index** (per issue #1): the vault + per-chunk SHA256 values are sufficient to rebuild the table from scratch (walk all pages, chunk, hash, embed only chunks whose hash isn't already present, upsert) — consistent with "LanceDB is explicitly not primary storage."
- Architectural fit: because ingest already needs to run the two-step CoT off the PySide6 UI thread, the embedding call (network-bound, same shape as the CoT's own LLM calls) is a natural additional stage in that same background job/worker rather than a separate subsystem — decouples ingest latency from embedding-API latency and gives retries/backoff a natural home. (Not decided here — flagged for the ticket that designs the ingest pipeline's async/worker mechanism.)

## 5. Cloud embedding providers, OpenAI-compatible options, cost/dimensionality tradeoffs

All of the below fit "cloud API only, provider-agnostic": base URL + API key + model name, the same shape as a chat-completion abstraction, so one adapter interface can likely cover both.

| Provider / model | Endpoint style | Dimensions | Price (per 1M tokens) | Context window | Notes |
|---|---|---|---|---|---|
| OpenAI `text-embedding-3-small` | native OpenAI `/v1/embeddings` | 1536 (truncatable) | ~$0.02 | 8191 tok | Cheapest OpenAI tier, reasonable default |
| OpenAI `text-embedding-3-large` | native OpenAI `/v1/embeddings` | 3072 (truncatable) | ~$0.13 | 8191 tok | Higher quality, higher storage/index cost |
| Voyage AI `voyage-3.5` / `voyage-4` family | own API, OpenAI-ish shape | Matryoshka: 2048/1024/512/256 | ~$0.02–0.06 (lite→standard), large ~$0.12 | 32K tok | Strong retrieval benchmarks; dimension is a runtime knob |
| Cohere `embed-v3` (English/multilingual) | own API, also via Bedrock/Azure | 1024 | ~$0.10 (light tier ~$0.02) | — | Mature, strong multilingual |
| Mistral `mistral-embed` | **OpenAI-compatible** `/v1/embeddings` | 1024 | ~$0.10 | 8192 tok | Easiest drop-in — literally mirrors OpenAI's request/response schema |
| Jina AI `jina-embeddings-v3/v5` | own API, OpenAI-compatible mode available | 1024, Matryoshka-truncatable to 32 | ~$0.02–0.05 | up to 32K tok | Cheapest at scale, multilingual + code variants |

- Lower dimensionality (256–1024) shrinks the LanceDB vector column and any ANN index; Matryoshka models (Voyage, Jina) let the app pick a dimension without re-embedding at a different model if the tradeoff needs revisiting later.
- OpenAI and Mistral are literally `/v1/embeddings`-shaped, so a provider-agnostic client already built for chat completions can likely reuse the same adapter pattern for embeddings with no new abstraction.
