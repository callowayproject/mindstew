# Review system detail

mindstew's Review system is a per-page, multi-flag inbox that sits in the full-window Review
Mode (decided in [#7](https://github.com/callowayproject/mindstew/issues/7)) and feeds off the
same background ingest pipeline built in
[#8](https://github.com/callowayproject/mindstew/issues/8). Flags persist in `ingest.db`
alongside the queue and knowledge-graph tables, get generated by a two-stage async sweep that
runs after the ingest queue drains, and are resolved through one universal action set. Structural
lint stays a separate surface with its own, mechanically-auto-fixable findings.

## Terms

- **review flag** — An item in the Review inbox raised against a page, one of five
  llm_wiki-derived types: `contradiction`, `duplicate`, `missing-page`, `confirm`, `suggestion`.
  (Avoid "review item" — llm_wiki's internal term, not used here.)
- **structural lint** — Deterministic, mechanically auto-fixable checks (orphan pages, broken
  wikilinks, no-outlinks) surfaced in a separate Lint surface, not the Review inbox. (Avoid "lint
  flag" or "review lint" — the two systems are deliberately distinct.)

## Why

The map's Notes already scope in an "async review system" as part of llm_wiki's feature set, but
left three things unspecified: what actually generates a flag, what the dedicated Review Mode
(from #7) shows and lets you do with one, and how that relates to the separately-fogged Lint
operation. A research pass against llm_wiki's actual source grounded these decisions in how the
upstream project behaves today, rather than guessing.

## Locked decisions

- **Storage: a `review_flags` table in `ingest.db`.** Rejected alternatives: a frontmatter field
  (would pollute a vault file meant to stay clean Markdown+YAML) and a separate JSON/file store
  (adds a second persistence mechanism when `ingest.db` is already the single source of
  derived/rebuildable ingest-adjacent state, per #8 and #9).
- **Structural lint stays separate from the Review inbox.** Rejected: folding it into the unified
  Review Mode. Structural lint findings (orphan pages, broken wikilinks, no-outlinks) are
  deterministic and mechanically auto-fixable (rewrite a link, stub a page) — a different action
  model than the judgment-call review flags. Merging the two surfaces would force one UI to serve
  both jobs.
- **Dismiss persists a "won't-fix" marker, keyed by the same content-derived flag ID.** Rejected:
  copying llm_wiki's simpler outright-delete. llm_wiki's review-item IDs are content-derived
  (hash of type+title) and its post-ingest sweep can regenerate the same flag on unchanged
  content; its plain delete lets a dismissed flag silently resurface. `ingest.db` already gives a
  natural place to keep the marker with no extra infrastructure, closing a known rough edge in the
  upstream behavior.
- **Flag generation replicates llm_wiki's two-stage async sweep**, running after the ingest queue
  drains: a rule-based auto-resolve pass, then a capped, batched LLM semantic-judgment pass — both
  non-blocking, tracked through the existing activity indicator. Rejected: generating flags only
  inline during each page's ingest step. The map's Notes already call this an "async review
  system," and the sweep reuses the exact background QThread/asyncio loop already built for
  ingest (#8) instead of inventing a second mechanism; batching the LLM pass keeps it capped
  rather than run per-page.

## Routine choices

- **Flag granularity**: a page can carry multiple concurrent, independently-resolvable flags
  (not one page-level status) — different triggers need different resolutions.
- **Review Mode UI paradigm**: a flat inbox list of all open flags across the vault, sorted by
  recency, filterable by trigger type and by page.
- **Action model**: one universal action set applies to any flag regardless of trigger — accept
  (clears it, no change), dismiss (clears it, marks won't-fix per the Locked decision above),
  edit-and-resolve (jumps to the page in Preview, clears on save), re-ingest (re-queues the page).
- **Flag taxonomy**: adopt llm_wiki's five review types as-is — `contradiction`, `duplicate`,
  `missing-page`, `confirm`, `suggestion` — they map cleanly onto mindstew's existing CoT ingest
  and knowledge-graph judgment calls; no scope reason to diverge for v1.
- **Bespoke per-type actions**: none for v1, beyond the universal set. llm_wiki's "deep research"
  action is out of scope (Deep Research itself is already ruled out of scope on the map); its
  "save as new wiki page" action collapses into edit-and-resolve targeting a new file.
- **Re-ingest action wiring**: clicking re-ingest calls the existing `enqueue_ingest` pipeline
  (#8/#11) for a full re-run through normal ingest and the sweep, rather than a lighter
  judgment-only recheck — one pipeline, one place flags get generated, easier to keep in sync
  with the won't-fix marker.

## Verified facts

Established by researching llm_wiki's source (`src/stores/review-store.ts`,
`src/lib/lint.ts`, `src/stores/lint-store.ts`, `review-view.tsx`, `lint-view.tsx`,
`sweep-reviews.ts`, `lint-fixes.ts`):

- Review and lint are genuinely separate systems, not one feature under two names. Review's type
  union is `contradiction | duplicate | missing-page | confirm | suggestion`; lint's is
  `orphan | broken-link | no-outlinks` (structural) plus a `semantic` type that feeds review.
- Structural lint runs off-main-thread in a Web Worker and is manually/user-triggered, not
  automatic; semantic lint and the review sweep are both LLM-backed and run through the activity
  store.
- Review item IDs are a content-derived hash (`type::normalizedTitle`), so resolved state
  survives ingest regeneration; lint item IDs are simple incrementing counters and do not persist
  across runs — each lint run clears and repopulates.
- `sweep-reviews.ts` is the concrete mechanism behind the map's "async review system" label: it
  triggers when the ingest queue drains, runs non-blocking, and does rule-based auto-resolution
  first, then a capped batched LLM semantic-judgment pass (5 batches × 40 items).
- Lint has built-in mechanical auto-fixes (`appendWikilink`, `ensureBrokenLinkStub`,
  `rewriteWikilinkTarget`) that review items have no equivalent of.

## Risks

- Adopting llm_wiki's five-type taxonomy as-is (rather than designing mindstew's own) means any
  taxonomy gap discovered later requires revisiting this ticket's Locked decisions around storage
  and the sweep, since both were designed around this specific type set.
- The won't-fix marker is keyed to a content-derived ID; if the ID hashing scheme ever needs to
  change (e.g. to disambiguate near-duplicate titles), existing won't-fix markers could silently
  stop matching and previously-dismissed flags could resurface.
